实现原理

骨传导音乐 · BoneConduction — 用音频耦合触觉（Audio-coupled Haptics）让马达跟着系统声音振动

本文档 实现原理（通俗版） · 另有面向开发/AI 的完整构建蓝图： 实现规格书（AI 构建蓝图）→

本文档为项目自撰：依据 Android 公开 API 与 Ogg/Vorbis 公开规范，说明本项目代码的实际实现， 不含任何第三方分析文档的独家表述。涉及平台行为的部分以代码中的实测结论为准。

一、要解决的核心问题

Android 12（API 31）引入了音频耦合触觉：如果一段音频被标记为"带触觉声道"， 系统的音频 HAL 会把这条声道单独取出来，映射成振动电机的驱动波形。 于是"让马达跟音乐一起动"就有了官方通路——不需要自己调用 Vibrator， 而是把想要的振感当作一条音频声道播出去。

本项目的思路正是如此：抓取系统正在播放的声音 → 生成一条"触觉声道" → 编码成合法的 多声道 Ogg/Vorbis（并打上标记）→ 交回系统播放 → HAL 自动驱动马达。整条链路如下： 

系统正在播放的音频
   │  MediaProjection 授权
   ▼
[1] CaptureEngine   AudioRecord 内录（48k/16bit/立体声，URGENT_AUDIO 线程）
   ▼  每 4800 帧（100ms）一块
[2] HapticMixer     生成第 3 声道：高通塑形 + 动态压缩 + 削波
   ▼  聚合满 24000 帧（500ms）
[3] libhapticogg.so  libVorbis 编码 3 声道 Ogg，写 ANDROID_HAPTIC=1
   ▼  环形文件槽位
[4] SegmentPlayer   双 MediaPlayer 无缝接力，路由到听筒
   ▼
[5] 音频 HAL 分离第 3 声道 → 振动马达
（旁路）SessionMuter 把"原声"压掉，避免回声

二、采集层：把系统声音"接"过来

2.1 为什么必须走 MediaProjection

从 Android 10 起，录制其它应用的音频受严格管控，唯一合规途径是 MediaProjection（屏幕录制授权）。因此首次点击"开始"会弹出系统录屏确认框—— 这不是在录屏，而是获取音频回环（playback capture）的凭据。

2.2 只抓该抓的：按 Usage 过滤

AudioPlaybackCaptureConfiguration 允许指定"只抓哪些用途的声音"。本项目匹配 USAGE_MEDIA / USAGE_GAME / USAGE_UNKNOWN / USAGE_ASSISTANT， 即音乐、视频、游戏、语音助手；刻意不抓通话、通知提示等隐私音频，符合平台合规要求。 见 CaptureEngine.start()。

2.3 实时性与"整块读取"

线程优先级读取线程设为 THREAD_PRIORITY_URGENT_AUDIO，接近音频实时优先级。

整块读readFully() 会循环补齐，确保每次正好拿到 4800 帧（100ms），避免因部分读取导致下游帧数漂移。

防爆队列采集结果放入容量 4 的阻塞队列；队列满时丢最旧， 而不是阻塞——这是保证"延迟有上限"的第一道闸门。

三、触觉声道：怎么把声音变成"振感"

触觉声道的取值不是简单复制原声。原始立体声的低频能量通常远大于中高频， 若直接拿 (L+R) 驱动马达，会变成"低音轰炸"。因此在 HapticMixer.mix() 中做了三级处理：

3.1 第一步：高通塑形（Tone shaping）

用级联的一阶高通滤掉低频，让振感更多跟随中高频（人声、旋律、打击瞬态）。 一阶滤波器递推式： 

y[n] = a * ( y[n-1] + x[n] - x[n-1] )
a    = RC / (RC + 1),   RC = 1 / (2π·fc/fs)

级联 N 级可把滚降从 6 dB/倍频提高到 N×6 dB/倍频，本项目默认 HAPTIC_HIGHPASS_ORDER = 2、HAPTIC_HIGHPASS_HZ = 250。 另外用 HAPTIC_LOW_SHELF 混回少量原始低频，保留"身体感"。

3.2 第二步：动态压缩（Compressor）— 这是本项目对"音质/触发问题"的关键取舍

问题：只用"阈值门"（低于某音量就静音）会导致安静段落丢失； 只用"硬削波"又会在响段打底（顶到电机极限）。

解法：引入分块 RMS 压缩器——

  • RMS 低于阈值 COMPRESS_THRESHOLD=0.35：原样通过，安静段落完整保留；
  • RMS 高于阈值：按 COMPRESS_RATIO=3:1 压缩，把响段（尤其低音鼓）压住， 不再冲顶；
  • 增益按 attack/release 平滑（0.4 / 0.08），避免"抽吸"感。
若 rms > 阈值:
    target = (阈值 / rms) ^ (1 - 1/压缩比)
    compGain += 系数 × (target - compGain)   // 压缩时 attack，恢复时 release
否则:
    compGain 缓慢回到 1.0

3.3 第三步：软削波（避免硬削平）

即使压缩后仍有瞬时尖峰。硬削波（直接截断到 ±32767）会产生刺耳的"打底"失真； 本项目默认启用有理函数软削波，近似 tanh 的膝部曲线： 

f  = clamp(x / 32768, ±SOFT_CLIP_LIMIT)
y  = f · (f² + 27) / (9f² + 27)      // 平滑压缩，超过上限不再上扬
out= y · 32767

最终声道：out = [ L, R, haptic ]，第 3 声道才是驱动马达的信号。

3.4 音量与震动的关系

触觉输出电平由固定系数 HAPTIC_OUTPUT_SCALE 决定，并叠加压缩增益。 另设极低门槛 HAPTIC_GATE_RMS=0.02：只有接近真正静音（<2%）才彻底不震， 避免底噪引起持续微震。

四、编码层：让它成为"合法的触觉音频"

4.1 关键魔法串 ANDROID_HAPTIC=1

平台在解析 Vorbis 注释头（comment header）时，会查找一条恰好等于 ANDROID_HAPTIC=1 的条目；找到后即认为"这是触觉音频，最后一条声道是触觉声道"。 本项目在 haptic_ogg.cpp 中显式写入： 

vorbis_comment_add(&vc, "ENCODER=vorbis");
if (channels == 3)
    vorbis_comment_add(&vc, "ANDROID_HAPTIC=1");   // 必须完整、独立的一条

踩坑记录：曾用 vorbis_comment_add_tag() 拼接键值，结果写出的注释变成 粘连串（如 ENCODER=ENCODERANDROID_HAPTIC=1…），平台匹配失败 → 能播不震。改用 vorbis_comment_add() 写入完整字符串后解决。

4.2 libVorbis 编码流程

标准 VBR 流程：vorbis_encode_init_vbr() → 写头 → 分块喂入 （每块 1024 帧，归一化到 float）→ vorbis_analysis_wrote(…, 0) 结束流。 质量参数即界面的"编码质量"（0.05~1.0，默认 0.5），越高越清晰但编码越耗时。

为降低首播延迟，三个头页用 ogg_stream_flush 立即刷盘，使播放能尽早开始。

五、播放层：无缝接力 + 触觉路由

5.1 双 MediaPlayer 接力（Gapless）

500ms 一段若用单播放器会段间有缝。本项目用两个 MediaPlayer： 先播 cur，同时 cur.setNextMediaPlayer(next) 预挂下一段， 平台会在段末无间隙切换。完成回调里再把刚播完的设为 current、预挂新的下一段，如此循环。

关键约束：必须共享同一个 audio session。setNextMediaPlayer 的接力要求 两个播放器同 session，否则框架会拆掉旧 track（实测表现为"播约 90ms 就被 stop"， 链条随即断裂、震动消失）。因此本项目让每段 setAudioSessionId(sharedSessionId) 复用同一 session。

完成回调要兼容两种身份：共享 session 后， 完成回调可能是"下一个"播放器触发的，判断条件需同时覆盖 completed == cur 与 completed == next。

起播要预缓冲：攒够 START_PREBUFFER=2 段再起播， 否则编码器跟不上实时速度，在第一个 500ms 边界就会断流、路由被系统回收。

5.2 为什么必须路由到"听筒"

在部分（尤其是高通平台）设备上，音频 HAL 只在流走听筒通话路径时才把第 3 声道 转发给马达；走默认扬声器路径时该声道被直接丢弃 → 表现为"无震动"。

因此本项目 SegmentPlayer：

  • 用 AudioManager.setCommunicationDevice(内置听筒) 把输出强制走听筒；
  • 播放器的 AudioAttributes 用 USAGE_VOICE_COMMUNICATION—— 这是 setCommunicationDevice 能生效的前提；
  • pump 循环每 50ms 检查一次路由，掉了立刻重设（自愈）。

副作用：声音会从听筒出来、音量偏小，属正常现象（与原实现行为一致）。

5.3 防止自激回环

若不限制，我们播放的声音会被 MediaProjection 再次抓取 → 无限回环。 本项目设置 setAllowedCapturePolicy(ALLOW_CAPTURE_BY_NONE)， 并显式 setHapticChannelsMuted(false) 允许触觉声道输出。

六、消除回声：原声静音

因为我们是"抓取 → 重放"，用户会同时听到原始声 + 约 500ms 延迟的重放声，叠加成回声。 SessionMuter 的做法是：周期性读取外部音频会话列表，对每个外部会话挂载 一个 -80dB 的输入增益效果，把原声压掉。

环节做法
会话发现读取 dumpsys audio 的会话/UID 列表（需特权 shell）
静音手段首选 DynamicsProcessing 输入增益 -80dB；ROM 不支持时回退到反射调用隐藏的 Volume 效果（-96dB + MUTE）
自我保护绝不静音本项目自己的会话（用 ownSessionIds 排除）
降级无特权时静音不生效，用户会听到回声——这是预期降级，非崩溃

七、低延迟设计小结

环节取值目的
采集块4800 帧 / 100ms实时反馈粒度
分片时长500ms编码/播放平衡
待播上限6 片超限丢最旧，延迟不无限累积
起播预缓冲2 片防队列抽空、路由被回收
采集线程URGENT_AUDIO接近音频实时优先级
路由巡检50ms听筒路由掉了自愈

固有端到端延迟约 550~650ms（采集块 + 分片 + 编码 + 播放缓冲）。 可用界面的"对齐延迟"（±2000ms）在听感上做补偿，但无法从物理上彻底消除。
